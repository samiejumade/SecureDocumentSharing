1. Executive Summary
SecureDocChain is a blockchain-based document sharing platform purpose-built for three professional verticals — law firms, creative production houses, and business startups — where document confidentiality, tamper-evidence, and verifiable access control are mission-critical requirements.
Current tools such as Google Drive, Dropbox, and DocuSign rely on centralized servers that create single points of failure, require third-party trust, and offer limited audit capability. SecureDocChain replaces that dependency with a hybrid architecture: files are encrypted and stored on IPFS (a decentralized content-addressed network), while access rights, ownership records, and full audit logs are anchored on-chain using smart contracts. No centralized party can alter, delete, or secretly access a document.
Key Value Propositions
Tamper-proof documents — on-chain hashes detect any unauthorized modification
Immutable audit trail — every access, grant, and revocation is permanently recorded
No vendor lock-in — decentralized storage means no single provider controls your data
Attorney-client privilege & IP protection built into the architecture
Smart contract automation — time-locked access, auto-expiry, conditional sharing
Compliance-ready — GDPR, SOC 2, and bar association requirements addressed by design
2. Problem Statement
Each target vertical faces distinct yet related document security challenges that existing SaaS platforms fail to adequately address:
Law Firms
Legal documents — contracts, evidence, court filings, client communications — demand the highest levels of integrity and confidentiality. Yet most firms rely on email attachments or cloud storage with little to no cryptographic verification. Key pain points include:
No provable chain of custody for digitally shared documents
Risk of unauthorized edits without visible version history
Expensive e-discovery processes due to poor audit trails
Compliance gaps with GDPR, ABA Model Rules, and regional bar requirements
Creative Script Writers & Production Houses
Scripts, screenplays, and pre-release creative assets are extraordinarily valuable and highly leak-prone. Writers and studios need:
Timestamped proof of authorship to support IP and copyright claims
Granular access control (e.g., director can read; producer can annotate; distributor cannot access until deal closes)
Leak detection — knowing exactly who had access when a breach occurs
Smart-contract royalty enforcement without a middleman
Businesses & Startups
Startups regularly share sensitive documents — NDAs, pitch decks, term sheets, HR files — with investors, partners, and contractors. Common problems include:
Sharing pitch decks without knowing if or when they were opened
No audit trail for who has seen a confidential investor document
Revoking access after a deal falls through is unreliable with cloud links
Vendor lock-in to expensive enterprise document management platforms

5. Proposed System Architecture
SecureDocChain uses a three-layer architecture informed by the Nature 2024 two-chain framework and the arXiv IPFS proxy model:
Layer 1 — Storage (IPFS / Filecoin)
Files are never stored on-chain. Instead:
The file is encrypted client-side using AES-256 before upload
The encrypted file is pinned to IPFS via Pinata or Infura, generating a content identifier (CID)
Filecoin provides incentivized persistence for long-term archival (critical for legal documents)
The original file never leaves the user's device unencrypted
Layer 2 — Blockchain (Smart Contracts)
The blockchain stores only lightweight metadata:
Document hash (keccak256 of the CID + owner + timestamp) — enables tamper detection
Access control list (ACL) — wallet addresses or email-mapped identities with permission levels
Encrypted key references — the AES key, wrapped with the recipient's public key
Full event log — every grant, revoke, and access event emitted as on-chain events
For law firms requiring full privacy, Hyperledger Fabric channels ensure only consortium members see metadata. For startups and creatives, Polygon PoS provides low-cost public verification.
Layer 3 — Application (Frontend + Node.js Proxy)
The application layer handles user experience and group key management:
React frontend with wallet login (MetaMask / WalletConnect) or email magic link
Node.js proxy manages group key rotation on member add/remove without owner intervention
File viewer with watermarking (for creative assets) and annotation (for legal review)
Compliance export module that packages audit logs into GDPR / e-discovery formats
6. Core Smart Contract (Solidity)
The following is the deployable access-control contract that forms the foundation of the platform. It has been reviewed for security and tested on the Ethereum Sepolia testnet:
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;
 
contract SecureDocChain {
    struct Document {
        string ipfsCID;
        address owner;
        mapping(address => uint8) accessLevel;  // 0=none, 1=view, 2=edit, 3=sign
        uint256 timestamp;
        string docType;   // 'legal' | 'script' | 'business'
        uint256 expiry;   // 0 = no expiry
    }
 
    mapping(bytes32 => Document) public documents;
 
    event DocumentUploaded(bytes32 docHash, string ipfsCID, address owner, string docType);
    event AccessGranted(bytes32 docHash, address grantee, uint8 level);
    event AccessRevoked(bytes32 docHash, address grantee);
 
    function uploadDocument(string memory _ipfsCID, string memory _docType,
                           uint256 _expiry) public returns (bytes32) {
        bytes32 docHash = keccak256(abi.encodePacked(
            _ipfsCID, msg.sender, block.timestamp));
        documents[docHash].ipfsCID   = _ipfsCID;
        documents[docHash].owner     = msg.sender;
        documents[docHash].timestamp = block.timestamp;
        documents[docHash].docType   = _docType;
        documents[docHash].expiry    = _expiry;
        documents[docHash].accessLevel[msg.sender] = 3;  // owner gets full access
        emit DocumentUploaded(docHash, _ipfsCID, msg.sender, _docType);
        return docHash;
    }
 
    function grantAccess(bytes32 _docHash, address _user, uint8 _level) public {
        require(documents[_docHash].owner == msg.sender, 'Not owner');
        require(_level >= 1 && _level <= 3, 'Invalid level');
        documents[_docHash].accessLevel[_user] = _level;
        emit AccessGranted(_docHash, _user, _level);
    }
 
    function revokeAccess(bytes32 _docHash, address _user) public {
        require(documents[_docHash].owner == msg.sender, 'Not owner');
        documents[_docHash].accessLevel[_user] = 0;
        emit AccessRevoked(_docHash, _user);
    }
 
    function getDocument(bytes32 _docHash) public view returns (string memory, uint256) {
        require(documents[_docHash].accessLevel[msg.sender] >= 1, 'Not authorized');
        if (documents[_docHash].expiry > 0) {
            require(block.timestamp <= documents[_docHash].expiry, 'Access expired');
        }
        return (documents[_docHash].ipfsCID, documents[_docHash].timestamp);
    }
}

ScriptSafe Feature Set

Production Access Tiers: Writer (full), Director (read + annotate), Producer (read only), Distributor (locked until deal signed)

1. Product Vision
You are building SecureDocChain — a blockchain-based document sharing and management platform for three professional verticals: law firms, creative production houses, and business startups.
The platform solves a fundamental problem: professionals share highly sensitive documents using tools (email, Google Drive, Dropbox) that offer no cryptographic integrity guarantees, no immutable audit trail, and no true access revocation. SecureDocChain fixes this with a hybrid architecture where files are encrypted and stored on IPFS, while access rights, ownership, and audit history are anchored immutably on a blockchain via smart contracts.
The One-Line Pitch
SecureDocChain = Google Drive + DocuSign + an immutable audit ledger, powered by blockchain — no third party can alter, delete, or secretly access your documents.
Design Principles
Security by default — AES-256 encryption before any file leaves the user's device
Decentralized trust — no single server, no single point of failure, no vendor lock-in
User-first UX — non-crypto users must be able to share a document in under 60 seconds
Vertical-aware — each of the three verticals (law, creative, startup) gets a tailored UI mode
Audit-first — every action is logged; nothing can be hidden or retroactively altered
2. System Architecture to Build
Build a three-layer hybrid architecture. This is the established standard from peer-reviewed research (Nature 2024, arXiv 2022, Hyperledger EECS 2024) and must not be changed to a purely centralized or purely on-chain approach.
Layer 1 — Encrypted Decentralized Storage (IPFS)
Client-side AES-256-GCM encryption before upload (the raw file never leaves the device unencrypted)
Upload encrypted blob to IPFS via Pinata API; store the returned CID (content identifier)
Filecoin integration in Phase 2 for incentivized long-term pinning
File sizes up to 500MB supported; chunking for files over 50MB
Layer 2 — Blockchain Smart Contracts
Store only: document hash (keccak256), IPFS CID, owner address, access list, encrypted key references, and timestamps
Never store raw file content or unencrypted keys on-chain
Deploy on Ethereum Sepolia testnet for development; Polygon PoS for production
Hyperledger Fabric mode for law firm enterprise deployments (permissioned, private channels)
All access events (grant, revoke, view) emitted as on-chain events — this is the audit trail
Layer 3 — Application (Frontend + Key Proxy)
React 18 frontend — three distinct UI modes selectable at login: LegalVault / ScriptSafe / VaultDesk
Node.js + Express key proxy service — handles group key management and re-keying on member changes
Authentication: MetaMask / WalletConnect for Web3 users; email magic link for non-crypto users
React Native app for iOS/Android (Phase 2 — weeks 11–14)
3. Smart Contract Specification
Implement the following Solidity contract as the core access control layer. This is the reference implementation — extend it but do not remove any of the listed functions or events:
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;
 
contract SecureDocChain {
 
    struct Document {
        string  ipfsCID;
        address owner;
        // 0 = no access, 1 = view, 2 = edit/annotate, 3 = sign/full
        mapping(address => uint8) accessLevel;
        uint256 timestamp;
        string  docType;   // 'legal' | 'script' | 'business'
        uint256 expiry;    // Unix timestamp; 0 = never expires
        bool    ipTimestamp; // true if registered as IP proof
    }
 
    mapping(bytes32 => Document) public documents;
    mapping(bytes32 => address[]) public accessLog; // ordered access history
 
    event DocumentUploaded(bytes32 indexed docHash, string ipfsCID,
                           address indexed owner, string docType, uint256 ts);
    event AccessGranted(bytes32 indexed docHash, address indexed grantee, uint8 level);
    event AccessRevoked(bytes32 indexed docHash, address indexed grantee);
    event DocumentAccessed(bytes32 indexed docHash, address indexed accessor, uint256 ts);
 
    function uploadDocument(string memory _cid, string memory _docType,
                            uint256 _expiry, bool _ipTimestamp)
        public returns (bytes32)
    {
        bytes32 docHash = keccak256(abi.encodePacked(_cid, msg.sender, block.timestamp));
        Document storage d  = documents[docHash];
        d.ipfsCID           = _cid;
        d.owner             = msg.sender;
        d.timestamp         = block.timestamp;
        d.docType           = _docType;
        d.expiry            = _expiry;
        d.ipTimestamp       = _ipTimestamp;
        d.accessLevel[msg.sender] = 3;
        emit DocumentUploaded(docHash, _cid, msg.sender, _docType, block.timestamp);
        return docHash;
    }
 
    function grantAccess(bytes32 _dh, address _user, uint8 _level) public {
        require(documents[_dh].owner == msg.sender, 'Not owner');
        require(_level >= 1 && _level <= 3, 'Bad level');
        documents[_dh].accessLevel[_user] = _level;
        emit AccessGranted(_dh, _user, _level);
    }
 
    function revokeAccess(bytes32 _dh, address _user) public {
        require(documents[_dh].owner == msg.sender, 'Not owner');
        documents[_dh].accessLevel[_user] = 0;
        emit AccessRevoked(_dh, _user);
    }
 
    function getDocument(bytes32 _dh) public returns (string memory, uint256) {
        require(documents[_dh].accessLevel[msg.sender] >= 1, 'Unauthorized');
        if (documents[_dh].expiry > 0) {
            require(block.timestamp <= documents[_dh].expiry, 'Expired');
        }
        accessLog[_dh].push(msg.sender);
        emit DocumentAccessed(_dh, msg.sender, block.timestamp);
        return (documents[_dh].ipfsCID, documents[_dh].timestamp);
    }
 
    function verifyIntegrity(bytes32 _dh, string memory _cid) public view returns (bool) {
        return keccak256(abi.encodePacked(documents[_dh].ipfsCID)) ==
               keccak256(abi.encodePacked(_cid));
    }
}

Magic Link Access: non-crypto users access shared documents via email magic link — no wallet required on the recipient side; sender still gets full audit trail

6. UX & Design Requirements
SecureDocChain must feel like a premium SaaS product, not a crypto dApp. The majority of end users in the law and startup verticals will never have used a blockchain product. Design for them first.
Must Have in UX
Upload completes in < 5 seconds for docs under 10MB
Share flow: recipient invited by email address (not wallet address) — system creates/links wallet in background
Every encryption operation shows a clear progress state
Access granted/revoked shows instant UI feedback with on-chain confirmation toast
Audit log readable as a plain English timeline ('John viewed on April 13 at 2:14pm')
Mobile-responsive — full feature parity on tablet
Dark mode support from day one
Must NOT Have
No gas fee prompts visible to end users — abstract all gas costs behind the platform
No wallet address shown as primary identity — show name/email; wallet is internal
No blockchain jargon in UI copy ('smart contract', 'CID', 'hash') — use plain language
No loading spinners without explanatory text ('Securing your document...')
No document preview that allows screenshot without a watermark warning
No feature that requires the user to hold or buy cryptocurrency
Key User Flows to Design (provide wireframes for all)
Onboarding — vertical selection → account creation (email or wallet) → first document upload (guided, < 90 seconds)
Upload & Share — drag-drop upload → encryption progress → set access level → invite by email → confirm sharing → view CID + hash
Recipient Access — email notification → magic link → in-browser document viewer (no download by default) → watermark visible
Audit Review — owner opens audit log → timeline of all accesses → filter by date/user → export as PDF
Revoke Access — owner selects user → click Revoke → on-chain transaction → user immediately loses access → logged
IP Timestamp (ScriptSafe) — upload script → toggle 'Register as IP Proof' → on-chain hash published → download certificate PDF
E-Discovery Export (LegalVault) — select matter → choose date range → export EDRM XML + PDF audit report

9. Acceptance Criteria
The following criteria must all pass before any milestone is accepted and signed off:
Security
No raw file content is ever transmitted to any server unencrypted — verified by network inspection
No encryption keys are ever stored in plaintext in any database, log, or environment variable
Slither static analysis returns zero high-severity findings on all deployed contracts
Revoking access makes the document inaccessible within one block confirmation time (~2 seconds on Polygon)
Tamper detection: altering the encrypted file on IPFS must cause verifyIntegrity() to return false
Performance
Document upload and encryption for a 5MB file completes in under 8 seconds on a standard broadband connection
Document list page loads in under 2 seconds for a user with up to 500 documents
Smart contract calls (grant, revoke) confirm on Polygon within 5 seconds
Usability
A non-crypto user (no wallet, no blockchain experience) can receive and open a shared document using only an email link — no setup required
The upload → share flow for a returning user takes under 60 seconds — timed in usability testing
No blockchain terminology appears in any user-facing copy — reviewed and approved by product owner
Compliance
GDPR right-to-erasure: deleting a user's encryption key makes their documents permanently inaccessible — demonstrated in test
Audit log exports contain: document name, action, actor identity, timestamp, and transaction hash for every event
IP Timestamp certificates include: document hash, blockchain transaction hash, block number, timestamp, and owner wallet address
